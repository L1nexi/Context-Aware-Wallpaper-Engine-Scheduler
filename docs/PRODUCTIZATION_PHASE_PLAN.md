# 产品化转向简要规划

状态：草案，供确认范围与实施顺序；尚未进入实现。

## 目标

第一主要阶段完成配置产品化：用户只表达可理解的使用意图，应用负责把这些意图编译为调度器运行时配置。同时以 `history dump` 保留排错能力，并提供首次启动和后续修改所需的 setup GUI。

本阶段不实现壁纸聚类、个性化学习或通用 Wallpaper Engine 管理能力。

## 已确定边界

- 裸 `SchedulerConfig` 不再是用户编辑契约。
- 对外配置收窄为面向用户意图的 profile；内部权重、阈值、fallback 等由产品持有。
- `Profile Compiler` 根据 profile 生成完整且经过校验的运行时 `SchedulerConfig`。
- 不读取、导入或迁移旧六文件配置，也不提供迁移指引。
- 所有 Sensor 和 Policy 作为产品行为固定启用；不可用时使用已有运行时降级机制。
- Bottle 按现有进程结构保留，必要时调整；它负责静态界面与主进程之间的本地通信。
- 配置修改通过显式应用操作进入调度器，不以文件变化监听作为正式流程。
- 调度器是运行时状态的唯一写入者；运行时替换发生在调度安全边界。

## 第一阶段：配置产品化

### 1. Profile 与编译边界

定义稳定、精简的 profile，只包含用户需要表达的意图：

- Wallpaper Engine 定位所需信息；
- 天气服务凭据与地点；
- 用户启用的内置场景；
- 内置场景与实际 playlist 的关联；
- 用户可理解的打扰设置，包括切换等待、空闲条件、全屏避让和性能负载约束；
- Activity 检测设置，包括需要识别的应用或窗口规则，以及它们对应的活动场景；
- setup 完成状态及必要的配置版本。

建立 `Profile Compiler`，集中持有内置场景、标签、权重、阈值和其他运行时默认值。编译结果是完整的 `SchedulerConfig`，调度器及 Policy 不直接读取 profile。

打扰设置和 Activity 检测仍属于 profile，但界面表达不直接复制 `SchedulingConfig`、`ActivityMatcherConfig` 等内部字段。`Profile Compiler` 负责把产品语义转换为相应的阈值、采样窗口和匹配规则。

### 2. 运行时修改与反馈

运行中从托盘打开设置时，界面读取当前已提交的 profile 及其版本，并在前端维护未保存草稿。用户确认修改后，通过 Bottle 本地接口提交一次 `ApplyProfile` 操作：

1. 主进程检查 profile 版本，拒绝覆盖已被其他窗口更新的版本；
2. 校验草稿并由 `Profile Compiler` 生成候选 `SchedulerConfig`；
3. 构造候选运行时，将应用操作交给调度器的单写者命令边界；
4. 在两个调度 tick 之间提交 profile 并替换运行时；
5. 向界面返回已提交的规范化 profile、新版本和应用结果。

字段输入错误直接关联到对应界面控件；编译、持久化或运行时构造失败时返回阶段和错误摘要，界面保留草稿供用户修改，已提交 profile 与当前运行时保持不变。成功时界面明确显示“已保存并生效”。应用配置本身不强制切换壁纸，后续动作仍由正常调度 tick 和打扰控制决定。

### 3. History dump

移除以持续可视化为目标的 Diagnostics 产品面，保留可导出的近期诊断事实。

第一版采用最直接的实现：沿用 `ui/dashboard_analysis.py` 中 `AnalysisStore` 的有界、线程安全 `TickTrace` 窗口，dump 命令读取当前窗口，并使用现有诊断映射生成一个 JSON 文件。不增加筛选、查询语言、聚合或多文件诊断包。

导出过程保留一个轻量 formatter 边界：store 只提供不可变窗口快照，默认 JSON formatter 负责输出结构和序列化。第一版只实现这一种 formatter，不建立插件系统；后续可以在不修改 store 和 dump 命令主流程的情况下增加人类可读文本、隐私裁剪或其他支持格式。

dump 直接覆盖现有 `TickTrace` 能提供的近期上下文、策略判断、匹配结果、执行决定、阻塞原因和执行结果，不额外拼接日志或构造新的诊断事实。

### 4. Setup GUI

setup GUI 使用 Vue、pywebview 和保留后的 Bottle 本地接口，覆盖两条路径：

- 首次启动没有有效 profile 时，完成 Wallpaper Engine、天气地点和场景 playlist 的必要设置；
- 运行中从托盘打开设置，读取当前 profile，修改后显式提交并等待应用结果。

初始界面只暴露产品语义，不提供 Sensor/Policy 开关、标签权重、阈值或通用配置树。地点输入应使用用户可理解的表达；自动定位的来源、权限和失败回退仍需单独决定。

设置界面至少包含 Wallpaper Engine、天气与地点、场景 playlist、打扰控制和 Activity 检测五组内容。运行时修改复用同一套 profile 表单和应用反馈，不提供另一套高级配置入口。

### 5. 旧产品面的收尾

- 删除旧 Diagnostics 页面及其高频查询契约；
- 删除面向用户手工编辑六个 YAML 的入口、示例和说明；
- 保留仍被 history dump 或运行时重建复用的 trace、映射和状态迁移能力；
- 更新启动流程、托盘入口、发布包内容、测试与 `AGENTS.md`，使其反映 profile 和 setup 成为唯一正式配置路径。

## 主要实施顺序

1. 确定 profile 契约和 `Profile Compiler` 输入输出。
2. 让调度器能够从编译结果启动，并通过单写者命令边界应用候选运行时。
3. 接入 profile 持久化、版本控制、错误反馈与 Bottle 设置接口。
4. 沿用近期 trace 存储，实现默认 JSON formatter 和 history dump。
5. 实现首次启动和运行时设置 GUI。
6. 删除旧配置与 Diagnostics 产品面，完成打包、文档和回归验证。

## 实施前需要明确的决策

- profile 的文件格式、版本字段和持久化位置；
- profile 保存与运行时替换的提交顺序，以及进程意外退出后的恢复规则；
- `Profile Compiler` 的默认值如何版本化，旧 profile 在产品升级后的解释规则；
- setup 是否限制为单窗口；profile 版本冲突已按拒绝覆盖处理；
- history dump 的窗口容量、默认保存位置和首版隐私裁剪规则；
- 地点自动获取所使用的数据源、权限提示和手动回退方式。

## 第一阶段完成标志

- 新用户无需接触内部配置即可完成 setup 并启动调度器；
- 运行中修改 profile 后可以得到明确的成功或错误结果，失败不破坏当前运行；
- 发布包和用户文档不再要求编辑六个 YAML；
- history dump 能导出足够复现近期调度判断的信息；
- 旧 Diagnostics 页面和旧配置入口退出正式产品路径。

## 后续展望：壁纸聚类与校准

在配置产品化稳定后，再评估将匹配粒度从 playlist 下沉到 wallpaper：建立稳定壁纸身份与预览事实，提取特征并聚类，以代表壁纸让用户对场景进行五级评价，再把校准结果接入调度。

这是一项工程量较大、需要独立决策与验证的后续工作，涉及特征来源、聚类稳定性、动态壁纸表示、增量更新、评价持久化、具体壁纸执行和推荐反馈等问题。它不属于第一阶段范围，也不在本规划中拆分实施任务。现有探索记录见 `half-finished/WALLPAPER_CLUSTER_CALIBRATION.md`。
