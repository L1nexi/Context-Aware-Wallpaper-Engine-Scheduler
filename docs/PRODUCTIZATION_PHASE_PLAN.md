# 产品化转向简要规划

状态：实施中；Profile 契约、原子持久化、运行时构造边界、独立的 `ProfileManager`、单写者应用队列、Bottle 接口、首次 Profile 创建、setup 场景目录与 playlist 扫描接口和 Tick History 导出已经建立；旧六 YAML 后端、配置 CLI、调参工具、样例和发布入口已经删除。

## 目标

第一主要阶段完成配置产品化：用户只表达可理解的使用意图，应用负责把这些意图编译为调度器运行时配置。同时以近期调度记录导出保留排错能力，并提供首次启动和后续修改所需的 setup GUI。

本阶段不实现壁纸聚类、个性化学习或通用 Wallpaper Engine 管理能力。

## 已确定边界

- 裸 `SchedulerConfig` 不再是用户编辑契约。
- 对外配置收窄为面向用户意图的 profile；用户只通过统一的响应风格选择产品权重预设，具体权重、阈值、fallback 等仍由产品持有。
- `Profile Compiler` 根据 profile 生成完整且经过校验的运行时 `SchedulerConfig`。
- 不读取、导入或迁移旧六文件配置，也不提供迁移指引。
- 所有 Sensor 和 Policy 作为产品行为固定启用；不可用时使用已有运行时降级机制。
- Bottle 按现有进程结构保留，必要时调整；它负责静态界面与主进程之间的本地通信。
- 配置修改通过显式应用操作进入调度器，不以文件变化监听作为正式流程。
- `ProfileManager` 独占 Profile 的读取、编译、持久化和应用队列，但不持有或代理 Engine。
- `WEScheduler` 根据配置目录创建并公开 `ProfileManager`，直接持有活动 Engine，并负责调度编排。
- Profile 应用命令由调度线程在运行时安全边界处理，活动 Engine 仍保持单写者语义。
- Profile 固定持久化为 `<config_dir>/profile.json`，由单写者队列串行更新并使用同目录原子替换，不使用乐观锁。

## 第一阶段：配置产品化

### 1. Profile 与编译边界

定义稳定、精简的 profile，只包含用户需要表达的意图：

- Wallpaper Engine 定位所需信息；
- 天气服务凭据与地点；
- 用户启用的内置场景；
- 内置场景与实际 playlist 的关联；
- 背景氛围与当前情境之间的响应风格；
- 启动等待、空闲条件、最长延后和壁纸轮换间隔四个确定时间值；
- Activity 检测设置，包括用户归类为工作或休闲的应用与窗口规则；
- setup 完成状态及必要的配置版本。

建立 `Profile Compiler`，集中持有内置场景、标签、权重、阈值和其他运行时默认值。编译结果是完整的 `SchedulerConfig`，调度器及 Policy 不直接读取 profile。

打扰设置和 Activity 检测仍属于 profile，但界面表达不直接复制 `SchedulingConfig`、`ActivityMatcherConfig` 等内部结构。打扰档位只是 setup 的快捷填值：用户选择档位时，界面把当前产品版本提供的四个预设数值写入表单，Profile 最终只保存这些确定数值；软件升级不会改变已保存值，用户再次选择档位时才会使用新版预设。`Profile Compiler` 只负责把分钟换算为运行时秒数，并固定启用全屏避让；CPU 阈值和采样窗口保留为内部默认值，不进入 profile。Activity 目标的规范化是 Profile 校验与 Policy 匹配共同依赖的领域规则，不由配置层反向调用具体 Policy 实现。

匹配设置只提供一个五档响应风格：从“背景优先”到“当前优先”，逐步降低季节背景的相对贡献，并提高天气和当前活动的相对贡献。Profile 保存 `response_style` 语义档位，`Profile Compiler` 将其展开为完整 Policy 权重组。不开放单 Policy 开关、单 Policy 权重或数字滑块。首版权重组是待内部 tuning 校准的暂定值，在正式发布前完成调优。

当前五档快捷值依次为：

| 档位       | 启动等待（秒） | 空闲等待（秒） | 最长延后（分钟） | 轮换间隔（分钟） |
| ---------- | -------------: | -------------: | ---------------: | ---------------: |
| eager      |              5 |             10 |               30 |                5 |
| responsive |             15 |             15 |               45 |               10 |
| balanced   |             15 |             20 |               60 |               15 |
| quiet      |             30 |             60 |              180 |               30 |
| minimal    |             60 |            120 |              300 |               60 |

### 2. 运行时修改与反馈

运行中从托盘打开设置时，界面读取当前已提交的 profile，并在前端维护未保存草稿。setup 限制为单窗口，托盘重复打开时聚焦已有窗口。用户确认修改后，通过 Bottle 本地接口提交一次 `ApplyProfile` 操作：

1. 主进程校验草稿并由 `Profile Compiler` 生成候选 `SchedulerConfig`；
2. 将应用操作交给 `ProfileManager` 的单写者命令队列，并在调度安全点构造候选运行时；
3. 在两个调度 tick 之间提交 profile 并替换运行时；
4. 向界面返回已提交的规范化 profile 和应用结果。

字段输入错误直接关联到对应界面控件；编译、候选运行时构造或持久化失败时返回阶段和错误摘要，界面保留草稿供用户修改，已提交 profile 与当前运行时保持不变。候选完整准备并成功持久化后，安装步骤只提交已经验证的运行时状态。成功时界面明确显示“已保存并生效”。应用配置本身不强制切换壁纸，后续动作仍由正常调度 tick 和打扰控制决定。

Bottle 请求只进行校验、入队并短暂等待结果；等待超时立即返回失败并取消尚未开始的命令，不引入异步任务查询或额外操作状态机。

### 3. Tick History

移除以持续可视化为目标的 Diagnostics 产品面，保留可导出的近期调度事实。

第一版采用最直接的实现：`core/state/tick_history.py` 中的 `TickHistoryStore` 在线程安全的有界窗口中保留 `TickTrace`，托盘操作读取当前窗口，并使用 `ui/tick_history.py` 的 DTO 映射生成一个 JSON 文件。不增加筛选、查询语言、聚合或多文件排错包。

导出过程保留一个轻量 formatter 边界：store 只提供不可变窗口快照，默认 JSON formatter 负责输出结构和序列化。第一版只实现这一种 formatter，不建立插件系统；后续可以在不修改 store 和 dump 命令主流程的情况下增加人类可读文本、隐私裁剪或其他支持格式。

导出内容直接覆盖现有 `TickTrace` 能提供的近期上下文、策略判断、匹配结果、执行决定、阻塞原因和执行结果，不额外拼接 Event Log 或构造新的调度事实。

默认保留并导出最近 1200 个 tick，文件写入 `data/tick-history/`，导出后直接打开。formatter 对 API Key 和地理位置字段脱敏；活动窗口、进程、playlist 和本机路径等排错信息保留。当前 `TickTrace` DTO 本身不包含 API Key 或地理位置，脱敏边界用于防止这些字段以后加入记录映射时被直接导出。

### 4. Setup GUI

setup GUI 使用 Vue、pywebview 和保留后的 Bottle 本地接口，覆盖两条路径：

- 首次启动没有有效 profile 时，完成 Wallpaper Engine、天气地点和场景绑定的必要设置；
- 运行中从托盘打开设置，读取当前 profile，修改后显式提交并等待应用结果。

后端已经提供固定 SceneId 目录、Wallpaper Engine playlist 扫描和首份 Profile 创建接口。首次创建会在落盘前完成编译与完整运行时组件准备；重复创建不会覆盖已有 Profile，任一阶段失败也不会留下半成品。启动宿主识别缺失 Profile、打开 setup 窗口并在创建成功后启动 Scheduler 的流程，与 GUI 一并接入。

初始界面只暴露产品语义，不提供 Sensor/Policy 开关、单 Policy 权重、标签权重、阈值或通用配置树；匹配偏好只显示统一的响应风格滑块。地点设置允许用户直接填写经纬度，也提供仅限 setup 的一次性自动定位辅助：按城市级别探测并填入经纬度，随后仍可手动修正。Profile 不保存自动定位开关，运行时不持续定位或自动更新位置。

设置界面至少包含 Wallpaper Engine、天气与地点、场景绑定、打扰控制和 Activity 检测五组内容。运行时修改复用同一套 profile 表单和应用反馈，不提供另一套高级配置入口。

### 5. 旧产品面的收尾

- 删除旧 Diagnostics 页面及其高频查询契约；
- 删除面向用户手工编辑六个 YAML 的入口、示例和说明；（已完成）
- 保留仍被 Tick History 导出或运行时重建复用的 trace、映射和状态迁移能力；
- 更新启动流程、托盘入口、发布包内容、测试与 `AGENTS.md`，使其反映 profile 和 setup 成为唯一正式配置路径。

## 主要实施顺序

1. 确定 profile 契约和 `Profile Compiler` 输入输出。
2. 让 `ProfileManager` 提供初始编译结果，并通过由调度线程消费的单写者命令边界应用候选运行时。
3. 接入 profile 持久化、错误反馈与 Bottle 设置接口。
4. 建立 Tick History 存储，实现默认 JSON formatter 和近期调度记录导出。（已完成）
5. 删除旧六 YAML 后端、配置 CLI、调参工具、样例与发布入口。（已完成）
6. 实现首次启动和运行时设置 GUI。
7. 删除旧 Diagnostics 产品面，完成前端宿主切换、打包、文档和回归验证。

## 第一阶段完成标志

- 新用户无需接触内部配置即可完成 setup 并启动调度器；
- 运行中修改 profile 后可以得到明确的成功或错误结果，失败不破坏当前运行；
- 发布包和用户文档不再要求编辑六个 YAML；
- Tick History 能导出足够复现近期调度判断的信息；
- 旧 Diagnostics 页面和旧配置入口退出正式产品路径。

## 后续展望：壁纸聚类与校准

在配置产品化稳定后，再评估将匹配粒度从 playlist 下沉到 wallpaper：建立稳定壁纸身份与预览事实，提取特征并聚类，以代表壁纸让用户对场景进行五级评价，再把校准结果接入调度。

这是一项工程量较大、需要独立决策与验证的后续工作，涉及特征来源、聚类稳定性、动态壁纸表示、增量更新、评价持久化、具体壁纸执行和推荐反馈等问题。它不属于第一阶段范围，也不在本规划中拆分实施任务。现有探索记录见 `half-finished/WALLPAPER_CLUSTER_CALIBRATION.md`。
