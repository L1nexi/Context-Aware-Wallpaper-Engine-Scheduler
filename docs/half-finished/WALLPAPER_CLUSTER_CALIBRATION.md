# Wallpaper 聚类与用户校准方向

状态：探索记录，不是实施规格或已批准路线图。

## 背景

现有调度器以 playlist 为匹配单位。这个模型可解释、可控制，但当壁纸数量增加后，用户很难继续手工组织 playlist 并维护标签权重。

诊断 GUI 也存在内在限制：调度器在非技术层面可解释的信息很少；展示内部数值又会要求用户理解匹配算法，造成抽象泄露。相比持续展示诊断信息，GUI 更适合作为 setup 和纠偏入口。

## 配置产品化

裸配置不再作为用户契约。用户通过 GUI setup 表达意图，应用据此生成内部 `SchedulerConfig`；权重、阈值、fallback 和其他高级参数继续存在于运行模型中，但不要求用户理解或编辑。后续只有在出现明确需求时，才考虑开放相应的语义化高级设置。

这是有意用部分自定义能力换取可用性。新版本不读取或导入旧六文件配置，也不提供迁移指引，首次启动统一进入 setup。

在引入聚类前，setup 提供当前十种内置场景：日间工作、日间休闲、夜间工作、夜间休闲、春季、夏季、秋季、冬季、黄昏和雨天。用户选择自己拥有的场景，并将其关联到实际的 Wallpaper Engine playlist；各场景的标签与权重由产品预设。

所有 Sensor 和 Policy 都是产品行为，始终启用，不向用户提供 `enabled` 开关。天气数据同时被 Time 与 Weather 策略消费，因此天气 API Key 和地点应作为 setup 的显式要求。Sensor 暂时不可用时沿用现有运行时降级机制，不改变这一配置原则。

## 方向

考虑把调度粒度逐步下沉到 wallpaper，并在 setup 中完成机器空间与用户语义之间的校准：

```text
壁纸预览图 -> 特征提取 -> 自动聚类 -> 展示代表壁纸
                                      -> 用户评价适用场景

当前上下文 -> 匹配已校准的聚类 -> 选择具体壁纸 -> openWallpaper
```

特征可以来自本地图像 embedding，也可以来自用户配置的多模态 API。模型只负责判断壁纸之间的相似性，不直接决定“适合夜间”“适合专注”等用户语义。

setup 为每个聚类展示多张代表壁纸，让用户针对少量生活场景选择“很不适合、不适合、中性、适合、很适合”。“中性”和“尚未评价”必须区分。聚类明显不一致时，用户还应能指出这一点。

这些聚类首先应是应用内部的虚拟分组，不写回 Wallpaper Engine 的 playlist。已经验证 `openWallpaper` 不会改变 Wallpaper Engine 记录的 selected playlist，因此 selected playlist 和当前 wallpaper 需要作为两类事实分别处理。

## 基本原则

- 机器负责压缩壁纸库，用户负责赋予场景含义。
- 首次 setup 的评价量应受控，剩余校准可以渐进完成。
- 特征提取和聚类是低频任务；调度运行时不应依赖在线模型。
- 用户对当前壁纸的反馈可以作为后续能力，但不在第一阶段引入自动学习。
- 聚类前由用户把内置场景关联到现有 playlist；聚类引入后，playlist 是否继续作为硬边界尚未决定。
- 不把这一方向扩张成完整的 Wallpaper Engine 管理器或通用推荐平台。

## 建议验证顺序

1. 建立 wallpaper 清单、稳定身份、预览图和当前 wallpaper 事实层。
2. 对真实壁纸库生成特征与聚类，先输出代表图报告，人工判断聚类是否有意义。
3. 聚类质量成立后，再实现 setup 中的场景评价和校准结果持久化。
4. 最后才把聚类选择和具体 wallpaper 执行接入调度管线。

第一轮 POC 的核心问题不是选择哪种算法，而是：用户能否通过少量代表图理解一个聚类，并稳定地评价它适合哪些场景。

## 未决问题

- 第一版采用本地 embedding，还是用户配置的多模态 API。
- 聚类数量、代表样本和离群壁纸应如何处理。
- 新增或删除壁纸后，如何保持已有用户评价尽量稳定。
- 静态预览图对动态壁纸是否足够；何时需要多帧特征。
- 完成校准后，现有 playlist 是硬边界、冷启动先验，还是逐步退出调度模型。
